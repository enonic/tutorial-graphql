= Subscriptions
:toc: right
:experimental:
:imagesdir: media/
:sourcedir: ../

On this page, we will explore how to add `Subscriptions`, which enable receiving real-time updates from a GraphQL server using long-lived requests.

A subscription differs from a query in what the engine gives back.
Where a query resolves to a value, a subscription resolves to a *publisher* that emits a result every time something happens.
GraphQL itself says nothing about how those results reach the client — that is the transport's job, and XP offers two: https://developer.enonic.com/docs/code/stable/web/sse[SSE] and https://developer.enonic.com/docs/code/stable/web/websocket[WebSocket].

We will use SSE. It is a plain HTTP GET that stays open, so it needs no handshake and can be watched with cURL.

To achieve this, we need to:

1. Add the necessary libraries for events and SSE provided by the Enonic Platform.
2. Create a GraphQL Subscription type and add it to our GraphQL schema.
3. Stream the subscription results from the API.

== Root Subscription GraphQL type

First of all, we should add the `lib-event` and the `lib-sse` dependencies to the `build.gradle` file.

.build.gradle
[source,kotlin]
----
include "com.enonic.xp:lib-event:${xpVersion}"
include "com.enonic.xp:lib-sse:${xpVersion}"
----

Creating a `Subscription` type is no different from creating a regular GraphQL Object type. In our example, for simplicity, we will use a field called `event` with the type `Json`.

./src/main/resources/apis/graphql/schema.ts
[source,ts]
----
const rootSubscriptionType = schemaGenerator.createObjectType({
    name: 'Subscription',
    fields: {
        event: {
            type: Json,
            resolve: () => {
                // Implementation
            },
        }
    }
});
----

We then add it to our schema using the subscription property:

./src/main/resources/apis/graphql/schema.ts
[source,ts]
----
const graphQLSchema = schemaGenerator.createSchema({
    query: rootQueryType,
    mutation: rootMutationType,
    subscription: rootSubscriptionType,
    dictionary: [noteType]
});
----

Now we just need to implement the `resolve` function to complete the GraphQL part.

The GraphQL Library provides functionality for creating a reactive processor for GraphQL publish streams using the `createPublishProcessor` function from its `+/lib/graphql-rx+` module. It also allows creating a subscriber via the `createSubscriber` function to handle operations such as subscribe, publish, connection, next, complete, etc., by processing push events to subscribers.

You can include the library as follows:

./src/main/resources/apis/graphql/schema.ts
[source,ts]
----
import {createPublishProcessor} from '/lib/graphql-rx';
----

We will also include the Event Lib to subscribe to events:

./src/main/resources/apis/graphql/schema.ts
[source,ts]
----
import {listener, send} from '/lib/xp/event';
----

The resolver's job is to return a processor that publishes the events we care about.
Create the processor and the event listener once, at module level, and let the resolver hand out the same processor every time.

IMPORTANT: Do not create them inside the resolver. It runs on every subscribe, so a processor and listener built there would be registered again for each client and never removed, leaking a listener per subscription.

./src/main/resources/apis/graphql/schema.ts
[source,ts]
----
const noteProcessor = createPublishProcessor();

listener({
    type: 'custom.note.*',
    callback: (event) => {
        noteProcessor.onNext(event);
    }
});

const rootSubscriptionType = schemaGenerator.createObjectType({
    name: 'Subscription',
    fields: {
        event: {
            type: Json,
            resolve: () => noteProcessor,
        }
    }
});
----

A single processor serves every subscriber.
When two subscription fields need different slices of the same stream, call `filter()` on the processor instead of creating another one.

To enable our `Subscription` to receive real messages, let's add event publishing for `note.created` and `note.deleted` within the resolve functions of the `createNote` and `deleteNote` Mutation fields, respectively. Below is an example for `createNote`. For `deleteNote`, the implementation will be similar, except the `type` will be `note.deleted`.

./src/main/resources/apis/graphql/schema.ts
[source,ts]
----
send({
    type: 'note.created',
    distributed: true,
    data: {
        note: note,
    }
});
----

The GraphQL part is ready.

== Stream the results

An SSE stream is opened by returning an `sse` object from a `GET` handler.
Our API already exports `POST` for queries and mutations; `GET` becomes the subscription stream, and XP picks the handler by request method.

The subscription document arrives as a query parameter, and we store it in `attributes` — per-connection state that XP hands back on every event for that connection:

./src/main/resources/apis/graphql/graphql.ts
[source,ts]
----
import {send} from '/lib/xp/sse';

interface StreamAttributes {
    query: string;
}

export function GET(req: Request): Response {
    const query = req.params.query;

    if (!query) {
        return {
            status: 400,
            contentType: 'application/json',
            body: {
                errors: [{message: 'Missing `query` parameter.'}]
            },
        };
    }

    return {
        sse: {
            attributes: {query: query}, // <1>
            retry: 5000, // <2>
        }
    };
}
----

<1> Carries the subscription document to the `sseEvent` handler. The handler receives no request, so without this there would be no way to know what the client asked for — short of keeping a map of connections, which is the bookkeeping we want to avoid.
<2> How long the client should wait before reconnecting, in milliseconds.

Opening the stream does not run the subscription. That happens when XP fires the `open` event, which is also where we get the `clientId` needed to send anything back:

./src/main/resources/apis/graphql/graphql.ts
[source,ts]
----
const subscribers: Record<string, Subscriber> = {};

export function sseEvent(event: SseEvent<StreamAttributes>): void {
    if (event.type === 'open') {
        openSubscription(event.clientId, event.attributes as StreamAttributes);
        return;
    }

    if (event.type === 'close') { // <1>
        cancelSubscription(event.clientId);
    }
}

function openSubscription(clientId: string, attributes: StreamAttributes): void {
    const result = execute(graphQLSchema, attributes.query);
    const publisher = result.data as Publisher | undefined; // <2>

    if (!publisher || typeof publisher.subscribe !== 'function') {
        send({
            clientId: clientId,
            message: {event: 'error', data: JSON.stringify(result)}
        });
        return;
    }

    const subscriber = createSubscriber({
        onNext: (executionResult) => { // <3>
            send({
                clientId: clientId,
                message: {event: 'next', data: JSON.stringify(executionResult)}
            });
        }
    });

    subscribers[clientId] = subscriber;
    publisher.subscribe(subscriber);
}

function cancelSubscription(clientId: string): void {
    const subscriber = subscribers[clientId];
    if (subscriber) {
        delete subscribers[clientId];
        subscriber.cancelSubscription();
    }
}
----

<1> `close` is terminal and fires after `timeout` and `error` as well, so it is the one place a subscription needs cancelling. Without it, a client that simply goes away leaves the processor delivering to nobody.
<2> For a subscription, `execute()` returns a publisher as `data` instead of a result object. A query or mutation sent to this endpoint would not, which is what the check below reports.
<3> Each event is a complete execution result — the same shape a query returns — so a client parses it the same way.

== Test the subscription

Open the stream in one terminal. cURL's `-N` disables buffering so events appear as they arrive, and `--data-urlencode` saves us encoding the document by hand:

[source,bash]
----
curl -N --get "http://localhost:8080/api/com.example.gqltutorial:graphql" \
  --data-urlencode 'query=subscription { event }'
----

The connection stays open with no output yet. In a second terminal, create a note:

[source,bash]
----
curl -X POST "http://localhost:8080/api/com.example.gqltutorial:graphql" \
  -H "Content-Type: application/json" \
  -d '{"query":"mutation { createNote(title: \"My Note\", content: \"Brief content\") { id } }"}'
----

The first terminal receives an event:

[source]
----
retry:5000

event:next
data:{"data":{"event":{"type":"custom.note.created","timestamp":1752491906282,"localOrigin":true,"distributed":true,"data":{"note":{"id":"2g6inpt0ybexu","title":"My Note","content":"Brief content","createdAt":"2026-08-13T11:18:26.281Z"}}}}}
----

Delete a note and a second event arrives. Stop the stream with kbd:[Ctrl+C]; the `close` event fires and the subscription is cancelled server-side.

NOTE: Standard GraphQL clients subscribe over a WebSocket using the `graphql-transport-ws` protocol rather than over SSE, because it lets one connection carry several operations chosen by the client. The `+/lib/graphql-rx+` page of the https://developer.enonic.com/docs/graphql-library[GraphQL Library documentation] covers that variant. The schema side is identical — only the transport changes.

That's it! In this chapter, we explored how to add Subscriptions and subscribe to real-time events using the capabilities of the Enonic Platform.

== Where to go next

You now have a complete GraphQL API: a schema with queries, mutations and subscriptions, served over HTTP from a universal API.

Before building anything real on top of it, revisit the shortcuts this tutorial took:

* Notes are kept in memory. Persist them with https://developer.enonic.com/docs/xp/stable/api/lib-content[lib-content] or https://developer.enonic.com/docs/xp/stable/api/lib-node[lib-node].
* The API allows `role:system.everyone`. Narrow the `allow` list in `graphql.yaml`, and authorize inside the resolvers using the context passed to `execute()`.
* Only a small part of the library is used here. The https://developer.enonic.com/docs/graphql-library[GraphQL Library documentation] also covers interfaces, unions, enums, input types and Relay-style connections.
