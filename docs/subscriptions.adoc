= Subscriptions
:toc: right
:experimental:
:imagesdir: media/
:sourcedir: ../

On this page, we will explore how to add `Subscriptions`, which enable receiving real-time updates from a GraphQL server using long-lived requests.

We will use the official `graphql-transport-ws` protocol from the GraphQL Foundation, as defined in the https://github.com/graphql/graphql-over-http/blob/main/rfcs/GraphQLOverWebSocket.md[GraphQL over WebSocket specification].
We choose a WebSocket because our client is GraphiQL, and standard GraphQL clients speak this protocol.
An API can serve subscriptions over https://developer.enonic.com/docs/code/stable/web/sse[SSE] instead when the consumer is your own code rather than a standard client, which needs less machinery than the handshake below.
The `/lib/graphql-rx` page of the https://developer.enonic.com/docs/graphql-library[GraphQL Library documentation] shows that variant.

To achieve this, we need to:

1. Add the necessary libraries for working with WebSockets and Events provided by the Enonic Platform.
2. Create a GraphQL Subscription type and add it to our GraphQL schema.
3. Add WebSocket support to our API.

== Root Subscription GraphQL type

First of all, we should add the `lib-websocket` and the `lib-event` dependencies to the `build.gradle` file.

.build.gradle
[source,kotlin]
----
include "com.enonic.xp:lib-event:${xpVersion}"
include "com.enonic.xp:lib-websocket:${xpVersion}"
----

Creating a `Subscription` type is no different from creating a regular GraphQL Object type. In our example, for simplicity, we will use a field called `event` with the type `Json`.

./src/main/resources/apis/graphql/schema.ts
[source,ts]
----
const rootSubscriptionType = schemaGenerator.createObjectType({
    name: 'Subscription',
    fields: {
        event: {
            type: Json,
            resolve: (env) => {
                // Implementation
            },
        }
    }
});
----

We then add it to our schema using the subscription property:

./src/main/resources/apis/graphql/schema.ts
[source,ts]
----
const graphQLSchema = schemaGenerator.createSchema({
    query: rootQueryType,
    mutation: rootMutationType,
    subscription: rootSubscriptionType,
    dictionary: [noteType]
});
----

Now we just need to implement the `resolve` function to complete the GraphQL part.

The GraphQL Library provides functionality for creating a reactive processor for GraphQL publish streams using the `createPublishProcessor` function from its `+/lib/graphql-rx+` module. It also allows creating a subscriber via the `createSubscriber` function to handle operations such as subscribe, publish, connection, next, complete, etc., by processing push events to subscribers.

You can include the library as follows:

./src/main/resources/apis/graphql/schema.ts
[source,ts]
----
import {createPublishProcessor} from '/lib/graphql-rx';
----

We will also include the Event Lib to subscribe to events:

./src/main/resources/apis/graphql/schema.ts
[source,ts]
----
import {listener, send} from '/lib/xp/event';
----

The resolver's job is to return a processor that publishes the events we care about.
Create the processor and the event listener once, at module level, and let the resolver hand out the same processor every time.

IMPORTANT: Do not create them inside the resolver. It runs on every subscribe, so a processor and listener built there would be registered again for each client and never removed, leaking a listener per subscription.

./src/main/resources/apis/graphql/schema.ts
[source,ts]
----
const noteProcessor = createPublishProcessor();

listener({
    type: 'custom.note.*',
    callback: (event) => {
        noteProcessor.onNext(event);
    }
});

const rootSubscriptionType = schemaGenerator.createObjectType({
    name: 'Subscription',
    fields: {
        event: {
            type: Json,
            resolve: () => noteProcessor,
        }
    }
});
----

A single processor serves every subscriber.
When two subscription fields need different slices of the same stream, call `filter()` on the processor instead of creating another one.

To enable our `Subscription` to receive real messages, let's add event publishing for `note.created` and `note.deleted` within the resolve functions of the `createNote` and `deleteNote` Mutation fields, respectively. Below is an example for `createNote`. For `deleteNote`, the implementation will be similar, except the `type` will be `note.deleted`.

./src/main/resources/apis/graphql/schema.ts
[source,ts]
----
send({
    type: 'note.created',
    distributed: true,
    data: {
        note: note,
    }
});
----

The GraphQL part is ready.

== Extend GraphQL API

Now we need to add https://developer.enonic.com/docs/code/stable/web/websocket[WebSocket] support to the controller of our GraphQL API.

To do this, we need to:

- Add an endpoint that will handle HTTP WebSocket requests
- Add a WebSocket event listener
- Generate a WebSocket URL and configure the WebSocket client for the GraphQL fetcher

We will add an events endpoint to our controller as follows:

./src/main/resources/apis/graphql/graphql.ts
[source,ts]
----
router.get('/events', (req) => {
    if (!req.webSocket) {
        return {
            status: 404
        };
    }
    return {
        webSocket: {
            subProtocols: ['graphql-transport-ws']
        }
    };
});
----

and add a WebSocket event handler:

./src/main/resources/apis/graphql/graphql.ts
[source,ts]
----
interface WebSocketEvent {
    type: string;
    message?: string;
    session: {id: string};
}

interface SubscribeMessage {
    type: string;
    id: string;
    payload: {query: string; variables?: unknown};
}

export function webSocketEvent(socketEvent: WebSocketEvent): void {
    if (!socketEvent) {
        return;
    }

    if (socketEvent.type === 'close') { // <1>
        cancelSessionSubscriptions(socketEvent.session.id);
        return;
    }

    if (socketEvent.type === 'message') {
        const message = JSON.parse(socketEvent.message as string) as SubscribeMessage;
        const sessionId = socketEvent.session.id;
        if (message.type === 'connection_init') {
            webSocketSend(sessionId, JSON.stringify({
                type: 'connection_ack'
            }));
        } else if (message.type === 'subscribe') {
            handleSubscribeMessage(sessionId, message);
        } else if (message.type === 'complete') {
            cancelSubscription(sessionId, message.id); // <2>
        } else {
            log.debug(`Unknown message type ${message.type}`);
        }
    }
}
----

<1> A client that simply goes away never sends `complete`, so the `close` event is what stops its subscriptions. Without this, every closed browser tab leaves a live subscription behind.
<2> A single socket can run several operations at once, each with its own `id`, so cancelling takes the operation id as well as the session.

Let's take a look at the implementation of the `handleSubscribeMessage` function, which handles messages of type `subscribe`.
Within this function, a GraphQL query is executed. For a subscription, its `data` property is a reactive `Publisher` (an `org.reactivestreams.Publisher`) that exposes a `subscribe` method.
We detect a subscription result by checking for that `subscribe` method, and then register a subscriber.

./src/main/resources/apis/graphql/graphql.ts
[source,ts]
----
import type {Subscriber} from '/lib/graphql-rx';

const graphQlSubscribers: Record<string, Subscriber> = {};

function subscriberKey(sessionId: string, operationId: string): string {
    return `${sessionId}|${operationId}`;
}

function handleSubscribeMessage(sessionId: string, message: SubscribeMessage): void {
    const payload = message.payload;

    const result = execute(graphQLSchema, payload.query, payload.variables);
    const data = result.data as {subscribe?: (subscriber: Subscriber) => void} | undefined; // <1>

    if (data && typeof data.subscribe === 'function') {
        cancelSubscription(sessionId, message.id); // <2>

        const subscriber = createSubscriber({
            onNext: (event) => {
                webSocketSend(sessionId, JSON.stringify({
                    type: 'next',
                    id: message.id,
                    payload: event,
                }));
            }
        });
        graphQlSubscribers[subscriberKey(sessionId, message.id)] = subscriber;
        data.subscribe(subscriber);
    }
}
----

<1> `execute()` types `data` as the result of any operation, so we narrow it before checking for `subscribe`.
<2> Cancels anything already running under the same operation id, so a client that re-subscribes does not leave the previous subscriber delivering in the background.

where `subscriber` sends the data to the client via WebSocket in the format expected by the https://github.com/graphql/graphql-over-http/blob/main/rfcs/GraphQLOverWebSocket.md#next[GraphQL over WebSocket protocol].

When an operation completes, and when the socket closes, the subscriptions must be cancelled.
Cancelling releases the subscriber so the processor stops delivering to a client that is no longer listening:

./src/main/resources/apis/graphql/graphql.ts
[source,ts]
----
function cancelSubscription(sessionId: string, operationId: string): void {
    const key = subscriberKey(sessionId, operationId);
    const subscriber = graphQlSubscribers[key];
    if (subscriber) {
        delete graphQlSubscribers[key];
        subscriber.cancelSubscription();
    }
}

function cancelSessionSubscriptions(sessionId: string): void {
    const prefix = `${sessionId}|`;
    Object.keys(graphQlSubscribers)
        .filter((key) => key.indexOf(prefix) === 0)
        .forEach((key) => {
            const subscriber = graphQlSubscribers[key];
            delete graphQlSubscribers[key];
            subscriber.cancelSubscription();
        });
}
----

As the final step, we need to generate a URL for the events API and assign it to the dataFetcher.

./src/main/resources/apis/graphql/graphql.ts
[source,ts]
----
router.get('/?', () => {
    const view = resolve('graphql.html');

    const handlerUrl = apiUrl({
        api: 'graphql'
    });

    const eventsUrl = apiUrl({ // <1>
        api: 'graphql',
        type: 'websocket'
    });

    const params = {
        handlerUrl: handlerUrl,
        eventsUrl: `${eventsUrl}/events`, // <2>
        playgroundCss: `${handlerUrl}/_static/style.css`,
        playgroundScript: `${handlerUrl}/_static/js/playground.mjs`,
    };

    return {
        status: 200,
        contentType: 'text/html',
        body: render(view, params)
    };
});
----

<1> Generates Events API URL
<2> Passes the `eventsUrl` to the rendering

./src/main/resources/apis/graphql/graphql.html
[source,html]
----
<div id="graphiql-container-wrapper" data-config-handler-url="{{handlerUrl}}" data-config-events-url="{{eventsUrl}}"></div>
----

.src/main/resources/static/js/playground.tsx
[source,ts]
----
const eventsUrl = container.dataset.configEventsUrl; // <1>

if (!handlerUrl || !eventsUrl) {
    throw new Error('Missing data-config-handler-url or data-config-events-url');
}

const fetcher = createGraphiQLFetcher({
    url: handlerUrl,
    wsClient: createClient({ // <2>
        url: eventsUrl, // <3>
    }),
});
----

<1> Read the WebSocket endpoint from the `data-config-events-url` attribute on the container element.
<2> Create a WebSocket client for handling GraphQL subscriptions.
<3> Point that client at the events endpoint.

The guard matters: `dataset` returns `undefined` for an attribute that is not there, and the fetcher requires a URL.
Failing here with a clear message beats letting an `undefined` URL surface later as a confusing connection error.

Now everything is ready — after deploying the changes, subscriptions should be available in our GraphQL schema.

That's it! In this chapter, we explored how to add Subscriptions and subscribe to real-time events using the capabilities of the Enonic Platform.

== Where to go next

You now have a complete GraphQL API: a schema with queries, mutations and subscriptions, served from a universal API, with a GraphiQL playground in front of it.

Before building anything real on top of it, revisit the shortcuts this tutorial took:

* Notes are kept in memory. Persist them with https://developer.enonic.com/docs/xp/stable/api/lib-content[lib-content] or https://developer.enonic.com/docs/xp/stable/api/lib-node[lib-node].
* The API allows `role:system.everyone`. Narrow the `allow` list in `graphql.yaml`, and authorize inside the resolvers using the context passed to `execute()`.
* Only a small part of the library is used here. The https://developer.enonic.com/docs/graphql-library[GraphQL Library documentation] also covers interfaces, unions, enums, input types and Relay-style connections.
