This section explains how to integrate the GraphiQL into your XP application. The GraphiQL offers a user-friendly web interface for writing and executing GraphQL queries, making it easier to test and debug your GraphQL API.

== Adding GraphiQL to the application

To enable the GraphiQL within our application, the following steps are required:

- Declare GraphiQL UI IDE dependencies in `package.json`
Add the necessary packages to support the GraphiQL user interface:

[source,json]
----
{
  "dependencies": {
    "@graphiql/react": "^<version>", // <1>
    "@graphiql/toolkit": "^<version>", // <2>
    "graphiql": "^<version>", // <3>
    "graphql-ws": "^<version>", // <4>
    "react": "^<version>", // <5>
    "react-dom": "^<version>" // <6>
  }
}
----

<1> `@graphiql/react` provides modular and reusable React components for building custom GraphiQL interfaces.
<2> `@graphiql/toolkit`	contains shared utility logic used by `@graphiql/react`, such as fetcher creation and schema handling.
<3> `graphiql` the main GraphiQL IDE package. Can be used directly for embedding the default GraphiQL experience or as a base for customization.
<4> `graphql-ws` required for enabling GraphQL subscriptions via WebSocket using the `graphql-ws` protocol.
<5> `react`	a peer dependency for all `@graphiql/*` packages. Needed to render the UI.
<6> `react-dom`	React's DOM renderer.

Replace each `<version>` with the version you want to use.
Running the following command adds all six at their current versions and writes them into `package.json` for you:

  npm install @graphiql/react @graphiql/toolkit graphiql graphql-ws react react-dom

- Declare backend dependencies in `build.gradle`. Add dependencies required to serve static files, render the GraphiQL markup, and handle HTTP requests in the controller:

.build.gradle
[source,kotlin]
----
dependencies {
    include "com.enonic.xp:lib-portal:${xpVersion}" // <1>

    include "com.enonic.lib:lib-mustache:<version>" // <2>
    include "com.enonic.lib:lib-static:<version>" // <3>
    include "com.enonic.lib:lib-router:<version>" // <4>
}
----

<1>	`lib-portal` provides access to Enonic XP’s portal API, including URL building.
<2>	`lib-mustache` adds support for rendering templates using the Mustache syntax. Useful for server-side rendering of HTML views.
<3>	`lib-static` allows serving static resources (JavaScript, CSS, images, etc.) from the application.
<4>	`lib-router` provides a lightweight server-side router for handling HTTP requests with route-based logic. Useful for implementing custom endpoints (e.g. `/graphql`, `/graphiql` and etc).

== Where the client files go

Enonic XP has two libraries for serving files out of an application, and they expect different folders.

https://developer.enonic.com/docs/lib-asset[lib-asset]:: Serves `src/main/resources/assets/`, with fingerprinted URLs and immutable cache headers. Convenient, but it works only for sites, webapps and admin tools.
https://market.enonic.com/vendors/enonic/static-asset-lib[lib-static]:: Serves whichever folder you point it at, `src/main/resources/static/` by convention. It works anywhere, including from an API.

Our GraphQL API is a https://developer.enonic.com/docs/code/stable/web/apis[universal API], and lib-asset explicitly does not support serving assets from one.
So we use lib-static, and our client files belong in `static/`.

IMPORTANT: The folder name is not cosmetic. `assets/` is lib-asset's convention; putting files there and serving them with lib-static is the kind of mismatch that confuses the next person to read the code.

Create the folder now — it is where the browser-side code and styles will live:

  src/main/resources/static/

The build bundles everything under `static/` into `build/resources/main/static/`, which is what ends up in the application and what lib-static reads.

We are now ready to proceed with the implementation.

== Implementing the GraphQL Controller

Now we need to update our controller to handle GraphQL requests and render the GraphiQL UI.
The API has to answer on three different paths, so the single `POST` export from the previous chapter is replaced by an `all` export that hands every request to a router:

./src/main/resources/apis/graphql/graphql.ts
[source,ts]
----
import type {Request, Response} from '@enonic-types/core';
import {apiUrl} from '/lib/xp/portal';
import {execute} from '/lib/graphql';
import {render} from '/lib/mustache';
import {mappedRelativePath, requestHandler, RESPONSE_CACHE_CONTROL} from '/lib/enonic/static';
import newRouter from '/lib/router';
import graphQLSchema from './schema';

const router = newRouter();

export function all(req: Request): Response { // <1>
    return router.dispatch(req);
}

router.get('/_static/{path:.*}', (req) => { // <2>
    return requestHandler(
        req,
        {
            cacheControl: () => RESPONSE_CACHE_CONTROL.SAFE,
            index: false,
            root: '/static', // <3>
            relativePath: mappedRelativePath('/_static/'), // <4>
        }
    );
});

router.get('/?', () => { // <5>
    const view = resolve('graphql.html');

    const handlerUrl = apiUrl({
        api: 'graphql'
    });

    const params = {
        handlerUrl: handlerUrl,
        playgroundCss: `${handlerUrl}/_static/style.css`, // <6>
        playgroundScript: `${handlerUrl}/_static/js/playground.mjs`,
    };

    return {
        status: 200,
        contentType: 'text/html',
        body: render(view, params)
    };
});

router.post('/?', (req) => { // <7>
    const body = JSON.parse(req.body as string) as {query: string; variables?: unknown};
    const result = execute(graphQLSchema, body.query, body.variables);
    return {
        contentType: 'application/json',
        body: result,
    };
});
----

<1> Delegate all incoming requests to the router for further handling.
<2> Define an endpoint for serving static resources, e.g. `/api/com.example.gqltutorial:graphql/_static/js/playground.mjs`.
<3> Point lib-static at the `static/` folder in the built application.
<4> Strip the `+/_static/+` prefix from the request before looking the file up, so the URL prefix and the folder stay independent.
<5> Define an endpoint to serve the GraphiQL UI.
<6> These are the names the build emits: one bundled stylesheet at the root of `static/`, and the script as an ES module beside it. The `.mjs` extension is why `graphql.html` loads it with `<script type="module">`.
<7> Define an endpoint to handle GraphQL requests.

The GraphiQL UI should now be accessible at the endpoint GET http://localhost:8080/api/com.example.gqltutorial:graphql.

== Summary

In this example, we covered:

- How to add the GraphiQL UI to our application.
- Why an API serves its client files from `static/` with lib-static, rather than from `assets/` with lib-asset.
- How to implement an API with multiple endpoints using https://market.enonic.com/vendors/enonic/router-lib[lib-router].
- How to serve static resources using https://market.enonic.com/vendors/enonic/lib-static[lib-static].
- How to generate the apiUrl using https://developer.enonic.com/docs/xp/stable/api/lib-portal[lib-portal].
