In this section, we will go through an example of how to create a custom GraphQL API.

== GraphQL Library

In order to build your own GraphQL API using the Enonic XP Platform, you should use the https://developer.enonic.com/docs/graphql-library[GraphQL Library].
This library makes it easy to build custom types and manage the schema lifecycle.
Its documentation describes every function and constant used in this tutorial.

First of all, we should add the https://developer.enonic.com/docs/graphql-library[GraphQL Library] dependency to the `build.gradle` file.

.build.gradle
[source,kotlin]
----
include "com.enonic.lib:lib-graphql:<version>"
----

== Define GraphQL API

An Enonic XP application exposes its own HTTP endpoints as https://developer.enonic.com/docs/code/stable/web/apis[universal APIs].
The library builds and executes the schema; the universal API is what makes it reachable over HTTP.

To create our GraphQL API, we need to create a `graphql` directory inside `/src/main/resources/apis`.
Then, we must add a descriptor file named `graphql.yaml` and a controller file named `graphql.ts`.

./src/main/resources/apis/graphql/graphql.yaml
[source,yaml]
----
include::{sourcedir}/src/main/resources/apis/graphql/graphql.yaml[]
----

In the descriptor, we define which user roles will have access to the API, whether it should be mounted under `/api`, and optionally provide a `title` and `description`.

APIs are not mounted anywhere by default, so `mount` and `allow` are what make this one reachable at all.
Be aware that `allow` controls who may call the API and nothing more — it does not limit what a resolver returns.
This tutorial allows everyone, which is fine for a local sandbox.
A real API would name a narrower principal here and check permissions inside the resolvers that read or write data, using the context value passed to `execute()` to see who is calling.

== Define schema

Now we can focus on developing the GraphQL schema.
Our server-side code is TypeScript, so we import what we need from the library by name.

./src/main/resources/apis/graphql/schema.ts
[source,ts]
----
import {GraphQLString, newSchemaGenerator} from '/lib/graphql';
----

XP resolves `+/lib/graphql+` at runtime from the JAR we added to `build.gradle`, so this import is not a relative path into `node_modules` — it is the library as the platform sees it.

After that, we need to obtain an instance of `schemaGenerator` in order to define `types`, `input types`, the `schema`, `unions`, `enums`, `interfaces`, and more.

./src/main/resources/apis/graphql/schema.ts
[source,ts]
----
const schemaGenerator = newSchemaGenerator();
----

For simplicity, let’s start by creating a schema with a single field called `serverTime`.
This will allow us to see how a schema is defined and how to get the response when querying our API.

We will begin constructing the schema by defining the root Query object type.
This type serves as the entry point for all read operations in the GraphQL API and will contain the fields that clients can query.

./src/main/resources/apis/graphql/schema.ts
[source,ts]
----
const rootQueryType = schemaGenerator.createObjectType({ // <1>
    name: 'Query',
    fields: {
        serverTime: { // <2>
            type: GraphQLString,  // <3>
            resolve: () => new Date().toISOString() // <4>
        },
    },
});
----

<1> Defines the root `Query` object type, which specifies the fields that can be queried in the GraphQL API.
<2> Declares the `serverTime` field inside the root query type.
This is the name of the field that can be requested by GraphQL clients.
<3> Specifies the return type of the `serverTime` field.
In this case, it is a `GraphQLString`, meaning the field returns a string value.
<4> Defines the `resolver` function for the `serverTime` field.
This function is executed when the field is queried and returns the current server time in ISO 8601 format.

Next, we define the schema object itself.
The schema ties together the root Query type (and optionally Mutation and Subscription types) and serves as the core configuration for the GraphQL API.

./src/main/resources/apis/graphql/schema.ts
[source,ts]
----
const graphQLSchema = schemaGenerator.createSchema({ // <1>
    query: rootQueryType,
});

export default graphQLSchema; // <2>
----

<1> Creates a new GraphQL schema. This defines the overall structure of the API, starting with the root query type.

<2> Export the created GraphQL schema for use in the application.

Now that the schema is defined, let’s define the HTTP POST method for our API controller.
This method will handle incoming client requests and pass them to the GraphQL engine for execution.

./src/main/resources/apis/graphql/graphql.ts
[source,ts]
----
import type {Request, Response} from '@enonic-types/core';
import {execute} from '/lib/graphql';
import graphQLSchema from './schema';

export function POST(req: Request): Response {
    const body = JSON.parse(req.body as string) as {query: string; variables?: unknown};
    const result = execute(graphQLSchema, body.query, body.variables);
    return {
        contentType: 'application/json',
        body: result,
    };
}
----

The export name is the HTTP method: XP looks for an export matching the request's method, so `POST` handles our GraphQL requests.
A special `all` export catches any method without a handler of its own, which we will use in the next chapter to serve several endpoints from one API.

`Request` and `Response` come from `@enonic-types/core`, the package that types the XP runtime.
It is a development dependency only — nothing from it exists at runtime.

The complete example of the `schema.ts` is shown below.

./src/main/resources/apis/graphql/schema.ts
[source,ts]
----
import {GraphQLString, newSchemaGenerator} from '/lib/graphql';

const schemaGenerator = newSchemaGenerator();

const rootQueryType = schemaGenerator.createObjectType({
    name: 'Query',
    fields: {
        serverTime: {
            type: GraphQLString,
            resolve: () => new Date().toISOString()
        },
    },
});

const graphQLSchema = schemaGenerator.createSchema({
    query: rootQueryType,
});

export default graphQLSchema;
----

The application is now ready to be built, redeployed, and tested with the GraphQL API.

== Test GraphQL API

In the API descriptor `graphql.yaml`, we defined that the API is accessible to all users (allow: ["role:system.everyone"]) and is mounted at `/api` (`mount: ["web"]`).
As a result, the GraphQL API will be available at the following endpoint:

 /api/<appName>:<apiKey>

In our case, since the `appName` is `com.example.gqltutorial` and the `apiKey` is `graphql`, the endpoint becomes:

 /api/com.example.gqltutorial:graphql

For testing, we will use cURL.
It is assumed that cURL is already installed on your system.

[source,bash]
----
curl -X POST "http://localhost:8080/api/com.example.gqltutorial:graphql" -H "Content-Type: application/json" -d "{ \"query\": \"{ serverTime }\" }"
----

As a result of executing this command, you should see a response similar to the following:

[source,json]
----
{
   "data":{
     "serverTime":"2025-07-08T12:44:22.049Z"
   }
}
----

Great! We now have a working example of a simple GraphQL API.

== Handling errors

Not every request succeeds, and GraphQL reports failures in the response body rather than through the HTTP status code.
Ask for a field the schema does not define:

[source,bash]
----
curl -X POST "http://localhost:8080/api/com.example.gqltutorial:graphql" -H "Content-Type: application/json" -d "{ \"query\": \"{ notAField }\" }"
----

The query never runs, and the response carries an `errors` array instead of `data`:

[source,json]
----
{
   "errors":[
      {
         "errorType":"ValidationError",
         "message":"Validation error of type FieldUndefined: Field 'notAField' in type 'Query' is undefined"
      }
   ]
}
----

NOTE: The wording of `message` comes from the GraphQL engine and may change between versions. Match on `errorType` rather than on the message text.

A failing resolver behaves differently.
The field it serves resolves to `null`, the rest of the query still returns its values, and the response then contains *both* `data` and `errors`.
Clients must therefore check `errors` even when `data` is present — a `200` response does not mean everything succeeded.

The completed application also guards the request itself, returning `400` with an `errors` array when the body has no `query` property, so malformed requests fail in the same shape clients already handle.
